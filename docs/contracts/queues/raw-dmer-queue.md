
# `raw-dmer-queue`

| | |
|---|---|
| Type | Service Bus Queue |
| Producer | `intake-processor` |
| Consumer | `di-processor` |
| Max delivery count | 5 |
| Lock duration | 5 min |
| Duplicate detection window | 10 min (on `messageId`) |
| Dead-letter | Native `$DeadLetterQueue`; monitored by the `dlq-depth` alert (see `docs/operations/monitoring-alerts.md`) |

## Message envelope

```json
{
  "schemaVersion": "1.0",
  "sourceSystem": "mercury-batch | mercury-webhook",
  "documentUri": "https://... (our own blob storage, not Mercury's expiring pre-signed URL)",
  "receivedAt": "2026-08-05T12:00:00Z",
  "mercuryRecord": {
    "...": "the source system's own record for this DMER, embedded verbatim -- see below"
  }
}
```

Two kinds of fields, nothing duplicated between them:

- `schemaVersion`/`sourceSystem`/`documentUri`/`receivedAt` — owned/generated by
  `intake-processor` itself.
- `mercuryRecord` — the upstream record exactly as `intake-processor` received it, with
  zero fields picked out, renamed, or reshaped. The source system's response shape isn't
  this contract's to define, and it can change over time; `di-processor` reads whatever
  fields it needs directly off `mercuryRecord` rather than expecting `intake-processor` to
  have pre-extracted anything. For the Mercury batch path, this is currently a record
  shaped like:

  ```json
  {
    "dps_queue": "General",
    "document_guid": "123e4567-e89b-12d3-a456-426655440000",
    "document_name": "DMER-30004673 - DMFTTWO.pdf",
    "document_type": "DMER",
    "document_status": "Uploaded",
    "document_priority": "Regular",
    "received_date": "2024-10-03T07:11:00Z",
    "document_type_business_area": "Driver Fitness",
    "queue": "Team - Intake",
    "dmer_status": "",
    "document_url": "pre-signed URL -- what intake-processor downloaded from, not what documentUri points at",
    "driver": {
      "driver_id": "D1234",
      "first_name": "John",
      "middle_name": "",
      "last_name": "Doe",
      "licence_number": "12345",
      "documents": ["...historical/audit document entries -- not individually processed yet"]
    },
    "case": {
      "case_id": "C1234",
      "case_title": "30004673 - DMFTTWO - RSBC - 1",
      "case_type": "RSBC",
      "case_priority": "Regular",
      "case_owner": "Team - Intake",
      "case_status": "Open Pending Submission"
    }
  }
  ```

There's no `messageId`/`correlationId`/`documentId` field in the body: `document_guid`
(Mercury's own id for the DMER) is set as the Service Bus message's native `message_id`
property instead — read it via the SDK (`message.message_id`), not from the body.
`message_id` is the idempotency key — `di-processor` must no-op (not error) on a duplicate
`message_id` it has already completed. Likewise there's no separate `mercuryCaseId` field;
Mercury's own case id, when the DMER has one, is already at `mercuryRecord.case.case_id`.
